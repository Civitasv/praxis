# Feature-02 Praxis State Core

## Objective

Implement the Harness-neutral, project-local machine state that later Praxis Tutor, project-model, Codex, and DSH layers can safely share.

Feature-02 owns project-boundary discovery, `.praxis/state.json`, format validation, write locking, atomic replacement, compare-and-swap revisions, durable task identity/lifecycle, and a stable JSON CLI contract. It does not implement project fingerprints, `code.md`, `decisions.md`, Tutor behavior, or host lifecycle integration.

## Runtime layout

A Praxis-enabled project uses:

```text
<project>/.praxis/
├── state.json
└── .write-lock/   # transient while a writer holds the lock
```

`code.md` and `decisions.md` are added by later features.

The state directory and state file must be real project-local filesystem entries. Praxis refuses symlinked `.praxis` directories or `state.json` files rather than following them.

## Project boundary

`discover_project_root(cwd)` resolves the working directory and searches upward for the nearest `.git` marker. A `.git` directory, regular file, or symlink marker establishes a boundary without following the marker target. The nearest boundary wins, including nested repositories/worktrees.

If no Git boundary exists, the resolved current working directory itself is the project root; Praxis does not climb to an arbitrary parent looking for state.

## State schema

Format version starts at `1`.

```json
{
  "format_version": 1,
  "revision": 0,
  "enabled": true,
  "tasks": {}
}
```

Required top-level fields are exactly typed:

- `format_version`: integer, currently only `1`;
- `revision`: non-negative integer;
- `enabled`: boolean;
- `tasks`: object keyed by durable task id.

Unknown top-level fields are preserved across writes so later compatible metadata can coexist with older Feature-02 code.

Malformed JSON, invalid schema, and unsupported format versions are reported without replacing or resetting the original file.

## Revisions and compare-and-swap

The state revision is machine-owned. Every successful mutation of an existing state increments `revision` by exactly one.

Mutating APIs require the caller's `expected_revision`. Under the write lock Praxis re-reads current state and compares its revision. A mismatch returns a conflict and performs no write.

First initialization creates revision `0`. Installing Praxis does not initialize or enable a project; initialization occurs only through an explicit enable operation.

## Atomic writes

All state mutations run while holding the project write lock and replace `state.json` atomically from a temporary file in the same `.praxis` directory.

The write path is:

```text
serialize → temporary file → flush → fsync → os.replace
```

Where supported, Praxis also fsyncs the containing directory after replacement.

A failed serialization/write/replace is reported as failure and must not be reported as saved state.

## Write lock

Feature-02 uses a standard-library cross-process lock directory at `.praxis/.write-lock`.

Creating the lock directory is the atomic acquisition operation. A second writer waits up to a bounded timeout and then receives a lock-timeout error rather than writing concurrently. Releasing the lock removes only the lock directory owned by the current context.

Feature-02 never automatically steals an existing lock because it cannot prove that another writer is dead. Stale-lock recovery is a later operational enhancement.

## Task records

Task ids are generated by the Python core and use the form `task_<hex>`.

Each task record contains:

```json
{
  "host": "codex",
  "conversation_id": "optional-host-id",
  "stage": "understanding",
  "status": "active",
  "pending_choices": [],
  "title": "optional human-readable summary"
}
```

Allowed stages:

- `understanding`
- `design`
- `awaiting_decision`
- `implementation`
- `verification`
- `complete`
- `blocked`

Allowed statuses are `active`, `blocked`, and `complete`.

Task updates preserve fields not explicitly changed. Different tasks coexist in the same state. Completing one task must not alter another task's pending choices or stage.

## Enable / pause

`enabled: true` means Praxis project behavior may be restored by a host adapter. `enabled: false` means paused.

Pausing changes only the enabled flag and revision. It does not rewrite task decisions or imply completion. Re-enabling a paused project likewise preserves tasks.

## Core interfaces

Feature-02 introduces these neutral Python interfaces:

```text
praxis.project.discover_project_root(cwd) -> Path
praxis.state.load_state(project_root) -> dict | None
praxis.state.enable_state(project_root, expected_revision=None) -> dict
praxis.state.pause_state(project_root, expected_revision) -> dict
praxis.tasks.create_task(project_root, expected_revision, host, conversation_id=None, title=None) -> tuple[str, dict]
praxis.tasks.update_task(project_root, expected_revision, task_id, *, stage=None, status=None, pending_choices=None, title=None) -> dict
praxis.tasks.pending_tasks(state) -> dict
```

Mutating functions raise typed neutral exceptions for revision conflict, invalid/corrupt state, unsupported format, unsafe state paths, and lock timeout. Host adapters translate these errors later.

## CLI JSON contract

The neutral CLI adds:

```text
praxis status --cwd PATH
praxis enable --cwd PATH [--expected-revision N]
praxis pause --cwd PATH --expected-revision N
praxis task-create --cwd PATH --expected-revision N --host HOST [--conversation-id ID] [--title TITLE]
praxis task-update --cwd PATH --expected-revision N --task-id ID [--stage STAGE] [--status STATUS] [--pending-choice VALUE ...] [--title TITLE]
```

State commands emit one JSON object to stdout. Success objects include `ok: true`, the resolved project root, and the current state. Failures include `ok: false`, a stable error code, and a human-readable message; they exit non-zero.

`status` on a project with no state is successful and reports `active: false` with `state: null`. It does not create `.praxis/`.

## Acceptance criteria

### AC-001 — project isolation

Nearest Git/worktree boundaries win, no-Git projects use only the supplied cwd, and symlinked state paths are rejected.

### AC-002 — safe persistence

State writes are locked, atomic, revisioned, and malformed/unsupported state is preserved.

### AC-003 — compare-and-swap

A stale expected revision cannot overwrite a newer state.

### AC-004 — multi-task durability

Independent task records coexist; updating/completing one does not mutate another.

### AC-005 — pause semantics

Pause/resume preserves tasks and does not imply approval or completion.

### AC-006 — adapter-ready JSON

The CLI produces stable machine-readable success/error results without Harness-specific dependencies.

## Non-goals

- `code.md`, evidence fingerprints, stale-section detection, or section-level project-model revisions;
- `decisions.md` or Tutor decision provenance;
- Codex hooks/plugin packaging;
- DSH/Cordis runtime integration;
- stale-lock stealing/recovery;
- backend service, database, telemetry, model calls, UI, quizzes, or understanding scores.
